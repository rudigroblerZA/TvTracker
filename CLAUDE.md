# TvTracker

## Agent skills

### Issue tracker

Issues and specs live as markdown files under `.scratch/<feature>/` in this repo, not in GitHub Issues. See `docs/agents/issue-tracker.md`.

### Triage labels

The five default roles, recorded as a `Status:` line in each issue file: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one `GLOSSARY.md` at the repo root and decisions under `docs/adr/`, both created when first needed. See `docs/agents/domain.md`.

## Where things live

- A service's model, `DbContext`, design-time factory and migrations are in `src/Services/X/X.Data` (namespace `X.Data`), not in `X.API`. Add a migration with `dotnet ef migrations add <Name> --project src/Services/X/X.Data --output-dir Migrations`.
- The insight rules, their maths, the facts they read and their result types are in `src/TvTracker.InsightsEngine` (namespace `TvTracker.InsightsEngine`): the per-show ones (worth it, gets good, endings, forecasts, DNA, tags; `Shows/`, `Tags/`, `Forecasts/`) and the per-viewer ones (streaks, essential cut, catch-up, backlog, Year in TV, taste, taste twins, reunion radar and the rest; `Viewer/`, one file per insight). It has no database, HTTP, flag or messaging code and must not gain any. For per-show insights `Analytics.Worker/Insights` loads the facts (`InsightSourcesLoader`), runs the rules (`InsightsPipeline`), and writes the lists and publications. For per-viewer insights the endpoint in `Analytics.API/Apis` only loads the facts and calls the engine (`StreaksApi` → `Streaks`): a new rule, threshold or ordering goes in the engine, with a unit test in `tests/Analytics.UnitTests`, not in the endpoint.
- A table that holds something about a member (a column named like `UserId`, `FollowerId`, `SavedById`, `ModeratorId`, or their name beside it) must be dealt with in that service's handler of `UserDeletedIntegrationEvent`: deleted, or kept without their id and name. `tests/Privacy.IntegrationTests` fills every such table from the model, runs each service's handler and searches the database for the member, so a new table fails there until the handler covers it. A member-id column under a new kind of name is added to `MemberData`'s patterns. The same tables must be in that service's data export (`GET api/v1/me/export`): `ExportTests` there asks for the export and looks for each table's row, so a new table fails until it is exported or listed in the test as left out, with why (a copy of what another service exports, say).
- A handler of an integration event that changes the database makes its change through `db.HandleOnceAsync(e, handler, apply, ct)` (`src/TvTracker.Persistence/InboxExtensions.cs`), which skips an event already applied and saves the change and its mark in one transaction; it doesn't call `HasProcessedAsync`, `MarkProcessed` or `SaveChangesAsync` itself. `apply` is database work only; a call to another system goes before or after. Two kinds of handler are outside this: the notification fan-out (`NotificationFanOut.NotifyOnceAsync`), which marks an event only some of the time and saves in batches, and a handler whose whole change is the same done twice: set-based `ExecuteDelete`s or `ExecuteUpdate`s by a key with nothing added (most `UserDeletedIntegrationEvent` handlers). The handler name keys stored rows, so an existing one is never renamed; a new class handling several events uses `InboxExtensions.HandlerName<T>(e)`.
- A service that needs members' plans without asking Identity keeps `UserPlanCopy` (`src/TvTracker.Persistence/UserPlanCopies.cs`) and uses `src/TvTracker.UserPlans`: `PlanCopyHandlers<TContext>` keeps the copy, `AddCopiedUserPlans<TContext>()` reads it. An endpoint that enforces a plan limit asks `IUserPlans.AllowanceAsync(http)` and refuses with `PlanRefusal.Problem(...)`; it doesn't read the copy or the `plans` flag itself.
- A copy of what a member did (watches, follows) is repaired from the owner's snapshot with `SnapshotRepair.Of` (`src/TvTracker.IntegrationEvents/SnapshotRepair.cs`). Its rows are stamped with the event's `CreatedAt` or the snapshot's `TakenAtUtc`, never the copying service's own clock.
- Blend and Mixtape are one engine, in `src/Services/Catalog/Catalog.Mixes` (namespace `Catalog.Mixes`): the rules in `MixRules`, the queries in `ShowMixer`. It has no HTTP, flag or rate-limit code and must not gain any; the endpoints in `Catalog.API/Apis` only check input and shape the answer. A change to candidates or ranking goes in the engine with a test in `MixRulesTests` or `ShowMixerTests`, and comes with a before-and-after from `tvtracker-import mix-eval` (`docs/design/mix-pairs.json`).
- Search is `src/Services/Catalog/Catalog.Search` (namespace `Catalog.Search`): `TitleSearch` (by title and near-spelling), `SemanticSearch` (by meaning) and `ShowSearch`, which puts the three kinds of match in order and into pages. It has no HTTP, flag, rate-limit or provider-import code and must not gain any; the endpoint in `Catalog.API/Apis/CatalogApi.cs` applies the filters and hands it the shows to search. A change to matching, order or paging goes in the module with a test in `ShowSearchTests` or `TitleSearchTests`.
